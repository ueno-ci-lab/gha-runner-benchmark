# Blacksmith（GitHub Actions ランナー）検証まとめ

## 概要

GitHub Actions のジョブを GitHub 標準ランナーより速く・安く実行できるとされる外部ランナー **Blacksmith** を、Laravel アプリの CI で検証した。

- 公式サイト：https://www.blacksmith.sh/
- ダッシュボード：https://app.blacksmith.sh
- ドキュメント：https://docs.blacksmith.sh
- 検証リポジトリ：ueno-ci-lab/gha-runner-benchmark（private）

## 結論

- **Blacksmith 2vCPU は、GitHub 標準ランナーより速く、安い**
    - 全体の時間：23〜47% 短縮
    - 1 回あたりのコスト：33〜54% 削減
- **4vCPU にしても効果は小さい**（時間は 6〜9% 短縮、コストはほぼ 2 倍）。今の CI では 2vCPU が最もバランスが良い
- 導入はワークフローの `runs-on` を書き換えるだけで済む。ただし、新しいアカウントでは利用開始時に追加確認（審査）がある

## Blacksmith とは

- GitHub Actions のジョブを、Blacksmith のマシン上で実行するサービス（GitHub App として連携する）
- ワークフローの `runs-on` を `blacksmith-2vcpu-ubuntu-2404` などに変えるだけで使える
- Docker のレイヤーキャッシュや依存関係のキャッシュを、同じ基盤上に保存するため速い
- 単価：2vCPU あたり $0.004/分（GitHub 標準 Linux 2 コアは $0.006/分）。無料枠あり（最新の条件は料金ページで確認）
- リージョン：us-east、us-west、eu-west、eu-central（アジアはなし）

## 検証の条件

| 項目 | 内容 |
|---|---|
| アプリ | Laravel 13 / PHP 8.5（Docker）、タスク管理 API |
| CI の内容 | Docker イメージのビルド → Lint（Pint）・静的解析（Larastan）・テスト（PHPUnit 74 件）を並列実行 |
| 比較パターン | GitHub 標準 2vCPU / Blacksmith 2vCPU / Blacksmith 4vCPU |
| 回数 | 各パターンでコールド（キャッシュなし）10 回、ウォーム（キャッシュあり）10 回 |
| 実行方法 | 同じコミット・同じワークフローで 1 回ずつ順番に実行し、API から時間を集計 |
| 実施日 | GitHub 標準：2026-10-11、Blacksmith：2026-10-13 |

※GitHub 側の 4vCPU（larger runner）は Team / Enterprise プランが必要なため、比較対象外とした。

## 計測結果（中央値）

| 条件 | パターン | 全体 | ビルド | 待ち時間 | 1 回のコスト |
|---|---|---|---|---|---|
| コールド | GitHub 標準 2vCPU | 204 秒 | 131 秒 | 4 秒 | 約 $0.039 |
| コールド | Blacksmith 2vCPU | 108 秒（-47%） | 61 秒 | 9 秒 | 約 $0.018（-54%） |
| コールド | Blacksmith 4vCPU | 98 秒（-52%） | 54 秒 | 8.5 秒 | 約 $0.032（-18%） |
| ウォーム | GitHub 標準 2vCPU | 82 秒 | 19 秒 | 3 秒 | 約 $0.024 |
| ウォーム | Blacksmith 2vCPU | 63 秒（-23%） | 19 秒 | 9 秒 | 約 $0.016（-33%） |
| ウォーム | Blacksmith 4vCPU | 59.5 秒（-27%） | 17 秒 | 8 秒 | 約 $0.032（+33%） |

（括弧内は GitHub 標準 2vCPU との差。コストはジョブごとに分単位で切り上げて計算）

## 分かったこと

- **コールドでは約半分の時間**。イメージのビルドが 131 秒 → 61 秒になった
- **ウォームでは、ビルド時間は同じ**。差が出たのは各ジョブでのイメージの準備（42〜45 秒 → 16〜17 秒）で、キャッシュの読み込みが速い
- Lint・静的解析・テストのコマンド自体は 1〜4 秒で、どのパターンでもほぼ同じ。そのため **vCPU を増やしても効きにくい**
- **ランナーが割り当てられるまでの待ち時間は、Blacksmith のほうが長い**（3〜4 秒 → 約 9 秒）。ただし全体の差に比べれば小さい
- 全 60 回の実行がすべて成功し、ばらつきも小さかった

## 導入手順

1. Blacksmith に GitHub アカウントでログインし、GitHub App を Organization にインストールする
2. ワークフローの `runs-on` を変更する（例：`ubuntu-24.04` → `blacksmith-2vcpu-ubuntu-2404`）
3. Docker ビルドを使う場合は、Blacksmith 用のアクションに置き換えるとキャッシュが効く
    - `useblacksmith/setup-docker-builder@v1`
    - `useblacksmith/build-push-action@v2`
4. 1 回だけ実行して、ジョブがランナーに割り当てられることを確認する

## 注意点・つまずいたこと

- **作ったばかりの GitHub アカウント・Organization では、追加確認が必要だった**
    - ジョブが待ち状態のまま実行されず、ダッシュボードのホーム画面に「This account requires additional verification.」と表示されていた
    - サポートから利用目的・月の利用分数・リポジトリ・リージョンを聞かれ、回答後 1 日ほどで利用できるようになった
    - この件は公式ドキュメントに記載がなく、原因に気づくまで時間がかかった。**ジョブが動かないときは、まずダッシュボードのホーム画面を確認する**
- コードとジョブのログは Blacksmith のマシン上で処理されるため、社内のセキュリティ基準での確認が必要
- アジアのリージョンがないため、国内のサーバーと通信するジョブは遅くなる可能性がある
- 計測は 1 日分のみ。時間帯や曜日による変動は確認していない

## 今後の検討事項

- 実際の業務リポジトリで、試験的に導入して効果を確認する

- CI の構成改善（チェック系ジョブを 1 つにまとめてイメージの準備を 1 回にする）も、ランナーの変更と合わせて検討する
- セキュリティ面（SOC 2 などの認証、データの扱い）を確認する
