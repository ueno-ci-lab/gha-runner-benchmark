# 振り返り（KPT）

> 2026-10-13 更新。Blacksmith 2vCPU の計測が終わった時点の内容。

## Keep（良かった点・続けること）

- 開発用と CI 用を 1 つの Dockerfile で管理し、PHP のバージョンを確実に揃えられた
- リポジトリをインターフェース化したことで、DB をモックにしたテストが書きやすかった
- テスト中に SQL が発行されたら失敗させるガードを入れ、モック漏れを確実に検出できるようにした
- ワークフローを再利用型にしたことで、ランナーだけを変えて同じ処理を比較できる
- 計測条件を実行名に残し、集計を自動化したことで、20 回分の計測を手作業なしで CSV にできた
- 計測を 1 回ずつ順番に流し、実行同士が影響し合わないようにした
- 集計結果を API の生データと突き合わせて検証してから本計測に進んだ
- Blacksmith が動かない間も、GitHub 標準側の計測を先に進めて待ち時間を有効に使えた
- 問題の切り分けを、App のインストール状況・ランナーグループ・メンバー権限と順に API で確認しながら進めた
- 本計測の前に 1 回だけ動作確認してから、コールド・ウォーム各 10 回を流した。GitHub 標準と同じスクリプトと集計で比較できた
- サポートへの問い合わせでは、利用目的・月の分数・リージョンを具体的に答え、追加確認が 1 日ほどで済んだ

## Problem（課題・困ったこと）

- 別プロジェクトの MySQL とポートが衝突した（ローカル環境の使用ポートを事前に確認していなかった）
- MySQL の起動待ちを考慮しておらず、初回のマイグレーションが失敗した
- GitHub アカウントが 2 つあり、SSH の設定が同じ `Host github.com` だったため、意図しないアカウントで push しようとして失敗した
- Blacksmith の利用開始に、アカウントの追加確認（本人確認）が必要だった。作ったばかりの GitHub アカウントと Organization だったことが原因と考えられる。ジョブが拾われない原因が分かるまでに時間がかかった
- Blacksmith の追加確認について公式ドキュメントに記載がなく、ダッシュボードのホーム画面を見るまで原因に気づけなかった
- Blacksmith はランナーが割り当てられるまでの待ち時間が約 9 秒と、GitHub 標準（3〜4 秒）より長い
- チェック系ジョブの時間の大半が Docker イメージの準備で、CI 全体として無駄が大きい
- テストは DB をモックにしているため、Eloquent での実装（実際の SQL）は自動テストで確認できていない
- テストが 1 秒未満で終わるため、ランナーの CPU 性能の差が CI 時間に出にくい（実際、Blacksmith との差はほぼイメージのビルドと読み込みの速さによるものだった）

## Try（次に試すこと）

- Blacksmith 4vCPU も計測し、vCPU を増やしたときの時間とコストの変化を確認する（GitHub 側の 4vCPU は Free プランでは使えないため、GitHub 標準 2vCPU と比較する）
- 日や時間帯を変えて再計測し、結果が安定しているか確認する
- 動作確認の実行は計測結果と分けて記録する（今回はウォームの集計に、キャッシュが空の 1 回が混ざった）
- 新しいサービスを試すときは、最初にダッシュボードのホーム画面と通知を確認する
- 検証用の Organization は、利用歴のあるアカウントで作るか、事前にサービス側の利用条件を確認する
- 複数の GitHub アカウントを使う場合は、SSH の設定で別名ホスト（例：`github-ueno`）を使い分ける
- CI の構成改善として、チェック系ジョブを 1 つにまとめてイメージの準備を 1 回にする案を、比較が終わってから検討する
- CPU 性能の差も見たい場合は、テストの件数や処理の重さを増やす
- Eloquent での実装を確認する結合テストを、モックのテストとは別に用意するか検討する
- Compose の初期設定として、ポートの変更と MySQL の起動待ちを最初から入れておく
